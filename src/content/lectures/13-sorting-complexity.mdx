У лекціях 11–12 ми порівнювали методи сортування, рахуючи порівняння й обміни. Тепер зробимо це строго: навчимося
оцінювати, як кількість операцій алгоритму зростає зі збільшенням обсягу даних, познайомимося з асимптотичними
позначеннями $O$, $\Omega$, $\Theta$, розберемо, як аналізувати цикли й рекурсію, і доведемо, що жодне
сортування порівняннями не може бути швидшим за $n \log n$.

## Навіщо оцінювати складність

Час роботи програми залежить від комп'ютера, компілятора, завантаженості системи. Щоб порівнювати **алгоритми**,
а не комп'ютери, рахують кількість **елементарних операцій** (порівнянь, присвоювань, арифметичних дій) як функцію
від **розміру вхідних даних** $n$ — для сортування це кількість елементів масиву.

Така оцінка відповідає на головне практичне питання: **як поведеться алгоритм, коли даних стане більше?** Якщо
програма сортує тисячу записів за мілісекунду, чи впорається вона з мільйоном? Для алгоритму порядку $n^2$ час
зросте в мільйон разів (хвилини), для порядку $n \log n$ — приблизно у дві тисячі разів (частка секунди).

Складність буває:

- **часовою** — кількість операцій;
- **просторовою** (ємнісною) — обсяг додаткової пам'яті понад вхідні дані.

## Найкращий, середній і найгірший випадки

Навіть за однакового $n$ кількість операцій залежить від самих даних. Сортування вставками на відсортованому
масиві виконує $n - 1$ порівнянь, а на масиві у зворотному порядку — $\frac{n(n-1)}{2}$. Тому розрізняють:

- **найгірший випадок** — максимальна кількість операцій серед усіх входів розміру $n$. Це **гарантія**: алгоритм
  ніколи не працюватиме довше;
- **середній випадок** — середня кількість операцій за певного розподілу вхідних даних (зазвичай вважають усі
  перестановки рівноймовірними);
- **найкращий випадок** — мінімальна кількість операцій. Сама по собі мало що каже, але показує, наприклад, що
  вставки чудово працюють на майже відсортованих даних.

Для критичних застосувань (системи реального часу, захист від атак спеціально підібраними даними) важливий саме
найгірший випадок. Тому швидке сортування з поганим опорним елементом — ризик, а пірамідальне — ні.

## Асимптотичні позначення

Точна формула кількості операцій зазвичай громіздка, наприклад $T(n) = 3n^2 + 5n + 7$. Для великих $n$ важливий
лише старший член, та й сталий множник 3 залежить від того, що саме рахувати. Тому використовують асимптотичні
оцінки — поведінку функції з точністю до сталого множника при $n \to \infty$.

**Оцінка зверху** $O$ («O велике»):

$$
T(n) = O(g(n)) \iff \exists\, c > 0,\ n_0:\ T(n) \le c \cdot g(n) \text{ для всіх } n \ge n_0.
$$

Функція росте **не швидше** за $g(n)$. Наприклад, $3n^2 + 5n + 7 = O(n^2)$: для $n \ge 1$ маємо
$3n^2 + 5n + 7 \le 15n^2$ ($c = 15$, $n_0 = 1$).

**Оцінка знизу** $\Omega$:

$$
T(n) = \Omega(g(n)) \iff \exists\, c > 0,\ n_0:\ T(n) \ge c \cdot g(n) \text{ для всіх } n \ge n_0.
$$

Функція росте **не повільніше** за $g(n)$.

**Точна оцінка** $\Theta$: $T(n) = \Theta(g(n))$, якщо водночас $T(n) = O(g(n))$ і $T(n) = \Omega(g(n))$ —
функція росте **так само**, як $g(n)$. Наприклад, кількість порівнянь сортування вибором
$\frac{n(n-1)}{2} = \Theta(n^2)$.

Корисні правила:

- сталі множники відкидають: $O(5n) = O(n)$;
- у сумі лишають найшвидше зростаючий доданок: $O(n^2 + n \log n) = O(n^2)$;
- основа логарифма не важлива: $\log_2 n$ і $\lg n$ відрізняються сталим множником, тому пишуть просто $O(\log n)$.

## Класи складності

| Порядок | Назва | Приклад |
| --- | --- | --- |
| $O(1)$ | стала | доступ до елемента масиву за індексом |
| $O(\log n)$ | логарифмічна | бінарний пошук |
| $O(n)$ | лінійна | пошук максимуму, сортування підрахунком ($k \ll n$) |
| $O(n \log n)$ | «лінійно-логарифмічна» | сортування злиттям, пірамідальне |
| $O(n^2)$ | квадратична | прості сортування |
| $O(2^n)$ | експоненційна | перебір усіх підмножин |

Скільки це операцій:

| $n$ | $\log_2 n$ | $n \log_2 n$ | $n^2$ | $2^n$ |
| --- | --- | --- | --- | --- |
| 10 | 3,3 | 33 | 100 | 1024 |
| 100 | 6,6 | 664 | $10^4$ | $\approx 1{,}3 \cdot 10^{30}$ |
| 1000 | 10 | $\approx 10^4$ | $10^6$ | $\approx 10^{301}$ |
| $10^6$ | 20 | $\approx 2 \cdot 10^7$ | $10^{12}$ | — |

Якщо комп'ютер виконує близько $10^9$ простих операцій за секунду, то сортування мільйона елементів методом
$n \log n$ займе соті частки секунди, методом $n^2$ — близько 17 хвилин, а експоненційний перебір для $n = 100$ не
завершиться ніколи: $10^{30}$ операцій — це понад $10^{13}$ років.

## Як оцінювати алгоритми

### Цикли

- **Один цикл** на $n$ ітерацій з тілом $O(1)$ — $O(n)$.
- **Вкладені цикли** — кількості ітерацій перемножуються: два вкладені цикли по $n$ — $O(n^2)$.
- **Залежні межі.** У сортуванні вибором внутрішній цикл виконує $n - 1 - i$ ітерацій:

$$
\sum_{i=0}^{n-2} (n - 1 - i) = (n-1) + (n-2) + \dots + 1 = \frac{n(n-1)}{2} = \Theta(n^2).
$$

- **Ділення навпіл.** Цикл, у якому змінна щоразу зменшується вдвічі (`while (n > 1) n /= 2;`), виконується
  $\log_2 n$ разів — $O(\log n)$.
- **Послідовні частини** додаються: $O(n) + O(n^2) = O(n^2)$.

### Рекурсія

Для рекурсивних алгоритмів записують **рекурентне співвідношення**. Сортування злиттям розв'язує дві задачі
вдвічі меншого розміру й зливає результати за $cn$ операцій:

$$
T(n) = 2T\!\left(\frac n2\right) + cn, \qquad T(1) = c.
$$

Розгорнемо його, підставляючи формулу саму в себе (для $n = 2^k$):

$$
\begin{aligned}
T(n) &= 2T(n/2) + cn \\
&= 4T(n/4) + cn + cn \\
&= 8T(n/8) + 3cn \\
&\;\;\vdots \\
&= 2^k\, T(1) + k \cdot cn = cn + cn \log_2 n = \Theta(n \log n).
\end{aligned}
$$

На кожному з $\log_2 n$ рівнів рекурсії виконується загалом $cn$ роботи.

Для швидкого сортування в найгіршому випадку одна частина порожня:
$T(n) = T(n-1) + cn$, звідки $T(n) = c(n + (n-1) + \dots + 1) = \Theta(n^2)$.

## Нижня оцінка для сортування порівняннями

Чи можна придумати сортування порівняннями, швидше за $n \log n$? Ні — і це можна довести.

Будь-який алгоритм, що сортує лише порівнюючи елементи, можна зобразити **деревом рішень**: у кожному вузлі —
порівняння двох елементів, дві гілки — дві можливі відповіді, у кожному листку — одна з перестановок, яку
алгоритм видає як відповідь. Щоб правильно відсортувати будь-який масив, дерево має містити всі $n!$ перестановок,
тобто щонайменше $n!$ листків.

Двійкове дерево висоти $h$ має не більше $2^h$ листків. Отже,

$$
2^h \ge n! \quad\Rightarrow\quad h \ge \log_2 n!.
$$

Висота дерева — це кількість порівнянь у найгіршому випадку. За формулою Стірлінга
$\log_2 n! \approx n \log_2 n - 1{,}44\, n$, тож

$$
h = \Omega(n \log n).
$$

Для $n = 8$: $8! = 40320$, $\log_2 40320 \approx 15{,}3$ — будь-якому алгоритму знадобиться щонайменше 16 порівнянь у
найгіршому випадку. Сортування злиттям і пірамідальне **асимптотично оптимальні** серед порівняльних методів.

Обійти цю межу можна, лише якщо не порівнювати елементи, а використовувати їхню структуру — як сортування
підрахунком ($O(n + k)$) чи порозрядне сортування.

## Складність за пам'яттю і стійкість

Час — не єдиний ресурс. Сортування злиттям потребує додаткового масиву розміром $n$: для масиву в гігабайт —
ще гігабайт пам'яті. Швидке сортування потребує лише стеку рекурсії $O(\log n)$ у середньому, пірамідальне —
$O(1)$. Іноді саме пам'ять визначає вибір методу.

**Стійкість** (лекція 11) — окрема якісна характеристика. Стійкі методи (вставки, злиття, підрахунок) дають змогу
сортувати записи послідовно за кількома ключами.

## Експериментальна перевірка

Теоретичні оцінки варто підтверджувати вимірюваннями. У C++ час вимірюють бібліотекою `<chrono>`:

```cpp
#include <algorithm>
#include <chrono>
#include <iostream>
#include <random>
#include <vector>
using namespace std;

void insertionSort(vector<int>& a);   // з лекції 11

template <typename Sort>
double measureMs(Sort sortFunction, const vector<int>& data) {
    vector<int> a = data;                          // сортуємо копію
    auto start = chrono::steady_clock::now();
    sortFunction(a);
    auto finish = chrono::steady_clock::now();
    return chrono::duration<double, milli>(finish - start).count();
}

int main() {
    mt19937 rng(2024);
    for (int n : {1000, 2000, 4000, 8000, 16000}) {
        vector<int> data(n);
        for (int& x : data) x = rng();
        double tInsert = measureMs(insertionSort, data);
        double tStd = measureMs([](vector<int>& a) { sort(a.begin(), a.end()); }, data);
        cout << n << '\t' << tInsert << " ms\t" << tStd << " ms\n";
    }
}
```

Як читати результати:

- для алгоритму порядку $n^2$ **подвоєння** $n$ збільшує час приблизно **вчетверо**;
- для алгоритму порядку $n \log n$ — трохи більше ніж **удвічі**;
- дуже малі часи (частки мілісекунди) неточні — збільшуйте $n$ або повторюйте вимірювання кілька разів і беріть
  середнє чи медіану;
- компілюйте з оптимізацією (`-O2`), інакше вимірюєте переважно накладні витрати налагоджувальної збірки.

Докладно вимірювання виконуватимемо на практичному занятті 4.

## Підсумки

- Складність алгоритму — кількість операцій (часова) або обсяг додаткової пам'яті (просторова) як функція розміру
  входу $n$.
- Розрізняють найкращий, середній і найгірший випадки; найгірший дає гарантію.
- $O$ — оцінка зверху, $\Omega$ — знизу, $\Theta$ — точна; сталі множники й молодші доданки відкидають.
- Вкладені цикли перемножують кількість ітерацій; ділення навпіл дає $\log n$; рекурсію аналізують через
  рекурентні співвідношення.
- Будь-яке сортування порівняннями потребує $\Omega(n \log n)$ порівнянь у найгіршому випадку (дерево рішень);
  злиття й пірамідальне сортування оптимальні.
- Теоретичні оцінки перевіряють експериментом: подвоєння $n$ учетверо збільшує час квадратичного алгоритму.
